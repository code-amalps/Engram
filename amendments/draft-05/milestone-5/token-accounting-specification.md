### 1. Primary Experimental Metric

The primary outcome metric for evaluating token efficiency is:

$$\mathbf{T_{\text{task}}}: \text{Total model tokens consumed per successfully completed engineering task.}$$

$$\text{Where } C = 1.00 \text{ (100\% functional acceptance satisfied).}$$

#### Critical Standard: Context Package Size is Not Task Consumption
- In some literature, "token efficiency" is erroneously measured by comparing the size of the initial prompt or context window (e.g., comparing a 1,500-token Engram context with an 8,000-token whole-file dump).
- In this experiment, **context package size is strictly an experimental input, not a result**.
- True token efficiency is determined by the **sum of all model tokens across the entire multi-turn trajectory** required to achieve verified functional acceptance. If a small initial context causes the agent to wander across 15 turns of blind exploration, it is inefficient regardless of initial prompt brevity.

### 2. Provider Usage Extraction & Telemetry Mapping

All token metrics must be extracted directly from the authoritative, provider-reported model response usage objects. Telemetry must never rely on local tokenizer approximations or client-side estimates for primary billing metrics.

#### 2.1 Authoritative Provider Schema (OpenAI / Codex API Standard)
For each model interaction (turn $t \in [1, K]$), the response payload contains:
```json
{
  "usage": {
    "prompt_tokens": 28412,
    "completion_tokens": 645,
    "total_tokens": 29057,
    "prompt_tokens_details": {
      "cached_tokens": 24576
    },
    "completion_tokens_details": {
      "reasoning_tokens": 128
    }
  }
}
```

#### 2.2 Mathematical Definitions & Double-Counting Safeguards

To prevent mathematical distortion and double-counting:

1. **Prompt Tokens (Input):**
   $$I_t = \text{usage.prompt\_tokens}$$
   - Represents the complete input sequence processed by the model on turn $t$.

2. **Cached Input Tokens:**
   $$I_{\text{cached}, t} = \text{usage.prompt\_tokens\_details.cached\_tokens}$$
   - **Crucial Rule:** $I_{\text{cached}, t} \le I_t$. Cached tokens are a **subset** of prompt tokens, not an additional separate quantity. They must never be added to $I_t$.

3. **Uncached Input Tokens:**
   $$I_{\text{uncached}, t} = I_t - I_{\text{cached}, t}$$
   - Represents the net novel tokens transferred and processed on turn $t$.

4. **Completion Tokens (Output):**
   $$O_t = \text{usage.completion\_tokens}$$
   - Represents the total tokens emitted by the model on turn $t$.

5. **Reasoning Tokens:**
   $$O_{\text{reasoning}, t} = \text{usage.completion\_tokens\_details.reasoning\_tokens}$$
   - **Crucial Rule:** $O_{\text{reasoning}, t} \le O_t$. Reasoning tokens generated by reasoning models (e.g., `gpt-5.6-luna`, `o1`, `o3-mini`) are already accounted for inside `completion_tokens`. They must never be added to $O_t$.

6. **Single-Turn Total Tokens:**
   $$T_t = I_t + O_t = \text{usage.total\_tokens}$$

### 3. Trajectory Aggregation Formulas

For a task execution consisting of $K$ completed turns:

$$\text{Total Cumulative Task Tokens:} \quad T_{\text{task}} = \sum_{t=1}^{K} T_t = \sum_{t=1}^{K} (I_t + O_t)$$

$$\text{Cumulative Input Tokens:} \quad I_{\text{task}} = \sum_{t=1}^{K} I_t$$

$$\text{Cumulative Cached Input Tokens:} \quad I_{\text{cached, task}} = \sum_{t=1}^{K} I_{\text{cached}, t}$$

$$\text{Cumulative Uncached Input Tokens:} \quad I_{\text{uncached, task}} = \sum_{t=1}^{K} I_{\text{uncached}, t}$$

$$\text{Cumulative Output Tokens:} \quad O_{\text{task}} = \sum_{t=1}^{K} O_t$$

$$\text{Cumulative Reasoning Tokens:} \quad O_{\text{reasoning, task}} = \sum_{t=1}^{K} O_{\text{reasoning}, t}$$

### 4. Secondary Operational Metrics

In addition to primary token totals, the harness must capture:

1. **Total Number of Turns ($K$):** Number of request/response dialogue rounds between agent and environment.
2. **Total Tool Invocations ($N_{\text{tools}}$):** Total count of external tools called (file reads, shell commands, patch applications).
3. **Exploratory Tool Calls ($N_{\text{explore}}$):** Count of read-only exploration calls (`Get-Content`, `rg`, `ls`, `git diff`) before the first modifying write.
4. **Agent Wall-Clock Duration ($W_{\text{agent}}$):** Total elapsed time from agent spawn to process exit (seconds).
5. **Tokens per Acceptance Criterion:**
   $$\text{Efficiency Ratio} = \frac{T_{\text{task}}}{N_{\text{criteria passed}}}$$

### 5. Accounting for Local Preprocessing (Zero Model Inference)

Engram's local indexing (`engram analyze`) and context compilation (`engram prompt`) run strictly offline on the local CPU without querying external LLMs or consuming model tokens.

#### Accounting Rules:
1. **Zero Synthetic Token Attribution:** The harness must **never invent or attribute synthetic model tokens** to Engram's local preprocessing.
2. **Operational Cost Tracking:** Local preprocessing overhead must be measured and reported in independent physical units:
   - Indexing Wall-Clock Duration: $t_{\text{index}}$ (seconds)
   - Context Generation Wall-Clock Duration: $t_{\text{prompt}}$ (milliseconds)
   - SQLite Cache Footprint: $S_{\text{db}}$ (megabytes on disk)
   - Local CPU Time: $t_{\text{cpu}}$ (user and system CPU seconds)
3. **Reporting Separation:** In all summary tables, local operational costs are listed in a dedicated "Local Overhead" column, strictly segregated from "Model Token Consumption."
