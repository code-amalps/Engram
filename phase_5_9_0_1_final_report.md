### 1. Is the 2.5-million-token aggregate ceiling actually enforceable?
**Yes, via the Dynamic Two-Stage Dispatch Protocol.** While the underlying Python script runs as two independent processes, executing Invocation 2 with `--global-tokens-ceiling min(1500000, 2500000 - T_actual_A)` mathematically bounds aggregate consumption to $\le 2,500,000$ tokens.

### 2. Are both invocation budgets mathematically consistent?
**Yes.** Task A is allocated $1,000,000$ tokens ($955,000$ usable $+ 45,000$ reserve); Task B is allocated $1,500,000$ tokens ($1,455,000$ usable $+ 45,000$ reserve). The sum of both invocation budgets equals exactly $2,500,000$ tokens.

### 3. Is reserve accounting unambiguous?
**Yes.** The headroom reserve ($45,000$ tokens per invocation) is strictly **included within** the invocation budget as a protected floor. New turns and arms are blocked when remaining headroom $H_{\text{rem}} < 45,000$.

### 4. Can any in-flight request exceed the arm or global budget?
**Yes, bounded by a single turn.** Because pre-dispatch guards evaluate remaining headroom before an LLM turn is dispatched, a model response can exceed the ceiling by at most the model's maximum output token limit ($\le 16,384$ tokens). The maximum possible theoretical overshoot across both invocations is $32,768$ tokens.

### 5. Is the execution order generated by the real orchestrator?

`rng = random.Random(self.seed); rng.shuffle(order)`.
