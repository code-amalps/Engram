### 1. Fundamental Principle of Acceptance

$$\mathbf{\text{A run that consumes fewer tokens but fails functional acceptance is a FAILURE, not a saving.}}$$

Token savings calculations are mathematically and methodologically invalid unless both the baseline run and the treatment run achieve full functional acceptance:

$$C_{\text{run}} = 1.00 \quad \iff \quad \bigwedge_{i=0}^{4} \text{Gate}_i == \text{PASS}$$

If either arm in a matched pair achieves $C < 1.00$, the pair is classified as **Non-Accepted**, and its token differential is excluded from the primary efficiency savings rate.

---

### 2. Five-Gate Functional Verification Architecture

To eliminate subjective evaluator bias, every execution patch generated by either arm is subjected to a sequential, automated five-gate verification battery:

```
[Candidate Diff]
       |
       v
[ Gate 0: Compilation & Typecheck ]  ---> FAIL (Exit code != 0) ---> C = 0.00
       | PASS
       v
[ Gate 1: Baseline Regression Suite ] ---> FAIL (Pre-existing test broken) ---> C = 0.00
       | PASS
       v
[ Gate 2: Task Functional Suite ]     ---> FAIL (Requirement unmet) ---> C = 0.00
       | PASS
       v
[ Gate 3: Boundary & File Audit ]    ---> FAIL (Unauthorized file touched) ---> C = 0.00
       | PASS
       v
[ Gate 4: Blinded Code Review ]      ---> REJECT (Hacks/anti-patterns) ---> C = 0.00
       | APPROVE
       v
[ Final Correctness: C = 1.00 ]
```

---

### 3. Detailed Gate Definitions (Primary Task: Task 2)

#### Gate 0: Compilation and Typecheck Integrity
- **Command:** `cargo check --offline --all-targets`
- **Pass Criteria:**
  - Process exits with code 0.
  - Exactly 0 compiler errors.
  - Zero fatal linter rejections.

#### Gate 1: Baseline Regression Prevention
- **Command:** `cargo test --offline --lib compiler::tests && cargo test --offline --test scoped_query_routing_test`
- **Pass Criteria:**
  - All existing compiler and routing tests pass (12/12 passed).
  - No existing functionality or backward-compatible wrappers broken.

#### Gate 2: Task-Specific Functional Verification
- **Command:** `cargo test --offline --test commit_cache_invalidation_test`
- **Pass Criteria (Automated Suite):**
  - **REQ-1 (Schema Integrity):** `.engram/index.db` creates and maintains a `meta` table recording `git_commit_head`.
  - **REQ-2 (Drift Invalidation):** Simulating a commit transition invalidates stale file excerpts and triggers re-indexing.
  - **REQ-3 (Cache Clean Command):** `engram clean --cache` purges SQLite database while preserving `.engram/memories.json`.
  - **REQ-4 (Idempotency):** Repeated calls on fresh commits do not perform redundant SQLite writes.

#### Gate 3: Authorized Boundary Audit
- **Inspection Command:** `git diff --stat <baseline_commit>`
- **Pass Criteria:**
  - Edits strictly confined to authorized files:
    - `src/compiler.rs`
    - `src/analyzer.rs`
    - `src/main.rs`
    - `tests/commit_cache_invalidation_test.rs`
  - Zero modifications to:
    - `Cargo.toml` or `Cargo.lock` (no new external dependencies permitted).
    - Unrelated modules (`src/mcp.rs`, `src/hook.rs`, `src/ci_guard.rs`).
    - Golden repository or benchmark harness.

#### Gate 4: Blinded Code Quality and Architecture Review
To prevent confirmation bias, an independent evaluator (or separate coding agent instance) reviews the generated code patches under an anonymized, blinded protocol.

---

### 4. Blinded Evaluation Procedure

1. **Diff Extraction and Anonymization:**
   - The test orchestrator captures the raw patch from Arm A and Arm B:
     ```powershell
     git diff > arm_a.patch
     git diff > arm_b.patch
     ```
   - Telemetry metadata, directory paths, and commit messages identifying the arm or Engram involvement are scrubbed.
   - Patches are assigned random cryptonym identifiers:
     - `patch_alpha.patch`
     - `patch_beta.patch`
     *(Mapping stored in a sealed cryptographic envelope until review completion)*.

2. **Blinded Audit Checklist:**
   The reviewer inspects each patch against four objective criteria:
   - **Architectural Idiom:** Uses standard Rust patterns (`Result<T>`, proper error propagation via `anyhow`, safe SQLite transactions).
   - **Absence of Hardcoded Hacks:** No hardcoded commit hashes, paths, or mock bypasses written specifically to fool the test harness.
   - **Resource Safety:** Proper closing of database connections and file locks; no unbounded memory allocation.
   - **Maintainability:** Clear variable naming, documented comments, and conformity with existing repository coding standards.

3. **Unblinding and Score Recording:**
   Only after the evaluator records the binary rating (**APPROVE** / **REJECT**) for both `alpha` and `beta` is the envelope unsealed to map the score to the respective experimental arm.
